# Learning Rules

These rules complement the ownership boundaries in [LEARNER_CONTRACT.md](LEARNER_CONTRACT.md).

1. Understand before copying code.
2. Prefer the standard library before frameworks.
3. Every major concept needs an exercise.
4. Every production feature needs tests.
5. Every optimization needs measurement.
6. Every architecture decision needs a trade-off.
7. Failure scenarios are as important as happy paths.
8. Prefer simple systems until complexity is justified.
9. Code must be readable before it is clever.
10. Senior engineers must be able to explain why.

## Practice protocol

- Predict behavior before running code.
- Time-box research, then implement the smallest experiment that answers the question.
- Keep failed attempts and lessons in `notes.md`.
- Never mark a topic complete using reading alone.
- Revisit a topic after a week and again inside a project.
- Ask for hints in increasing strength: question, concept, pseudocode, review, then solution.

## Review protocol

A review should cover correctness, clarity, tests, operational behavior, security, performance assumptions, and rejected alternatives. “It works” is the start of review, not its conclusion.
